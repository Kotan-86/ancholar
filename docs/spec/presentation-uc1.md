## 1. 背景（Why）

### 1-1. 解決する課題

`GetDailyTimelineUseCase`（UC-1）および `TimelineDTO` はアプリケーション層まで実装済みであり、Phase 1 の縦切りとしてブロックを縦に積んだリスト表示までは実現している。しかし現状の画面は、

- 各ブロックの「長さ」が画面上の高さに反映されず、どのブロックが 1 日のどれだけを占めているかが分からない。
- WORK TIME の中にだけタイムグリッドがあり、1 日全体の時間軸として読み取れない。
- DOWN TIME / SLEEP TIME がきちんと確保できているかを、ひと目で判断できない。

プロダクトゴール（`docs/product-goal.md`）が求める「前夜の回復が守れているか、翌日の過ごし方が **ひと目で** 分かる」状態に達していない。

### 1-2. 達成したい状態

- 1 日全体（DOWN TIME 起点）を 1 本の縦軸グリッドとして描き、**WORK TIME を除く 6 ブロック** を **時間の長さに比例した高さ** の色付きカードとして並べる。これにより、DOWN TIME / SLEEP TIME の確保状況と 1 日の構成が、目盛りとの対比でひと目で分かる。
- **WORK TIME の区間は、ブロックカードを描かず空欄にする。** 勤務時間そのものではなく、そこに入っている仕事用タスクだけを見せる（PO の実際のカレンダーの使い方に合わせた決定）。
- 見慣れた Google カレンダー（日表示・ダークテーマ）の操作感・視認性に寄せることで、学習コストなく読み取れる。
- ルール違反（`violations`）および社会的時差ぼけ警告（`socialJetLagWarning`）がユーザーに伝わる（初版から維持）。
- プレゼンテーション層は `TimelineDTO`（interface 層）のみを入力とし、アプリケーション層や Next.js 固有の配線に依存しない（初版から維持）。
- **1 日の総時間が日によって変わっても、同じ規則で読める。** 縦軸は `totalDurationMinutes` に比例し、1 時間あたりの高さ（48px）は変わらない。

### 1-3. Phase 1 のスコープ外

以下は本仕様の対象外とする。

- Google Calendar / Tasks API 連携および OAuth 認証
- 週次ビュー（土曜始まり）— 本スプリントでも対象外（PO 決定）
- UC-2〜5 の操作 UI（ドラッグ＆ドロップ、タスク追加等）
- PWA 化
- **現在時刻の赤線（now indicator）**（PO 決定: 再現しない）
- **ヘッダー上部の日付の丸バッジ**（PO 決定: 再現しない。日付ナビ自体は §2-2 のとおり再現する）
- **プライベートタスクの表示**（グリッド上にも、グリッド外のリストとしても表示しない。AC-4 を維持。将来表示する際の色 `#53839c` は §2-3-4 に記録のみ）
- **「共通」タスク（プライベートとパブリックの両方に属するタスク）の区別**。ドメインに概念がないため別 PBI の候補。色 `#606da1` は §2-3-4 に記録のみ
- **同時刻に重なる仕事用タスクの横分割表示**（Google カレンダー風の等分割）。Q-15 の決定により、Phase 1 は全幅で重ねる。等分割は別 PBI の候補
- **1 日の総時間が 23h / 25h になる日そのものの実現**（`docs/spec/day-duration.md` の PBI-C / PBI-D。未実装・仕様は未承認）。本仕様は、総時間が変わっても比例して描けることだけを要求する

## 2. 機能要件（What）

### 2-1. 表示対象データ

画面は UC-1 の戻り値 `TimelineDTO` を唯一の表示データ源とする。主要フィールドと表示上の意味は次のとおり。

| フィールド | 表示上の意味 |
| :--- | :--- |
| `anchorDate` | 1 日の起点（DOWN TIME 開始時刻）。タイムグリッドの 0%（上端）位置 |
| `totalDurationMinutes` | 1 日の総時間。グリッドの 100%（下端）位置の算出基準、およびグリッド全体の高さの算出基準。**表示側はこの値を固定値と見なさず、常に比例して描く**（標準の設定では 1440 分 = 24h。日によって 23h / 25h になりうる。P-6） |
| `blocks[]` | 7 つの時間ブロック（DOWN TIME 起点の時系列順）。**このうち `WORK_TIME` を除く 6 ブロックをカードとして描画する**（`WORK_TIME` はカードを描かない。§2-3-3） |
| `blocks[].blockId` | ブロック識別子（例: `DOWN_TIME`, `WORK_TIME`）。カードの表示名・配色・文字色の決定に用いる |
| `blocks[].startTime` / `endTime` | ブロックの開始・終了時刻。カードの縦位置・縦幅、およびカード内の時刻表記に用いる |
| `blocks[].durationMinutes` | ブロックの長さ（分）。**画面のどこにも分数として表示しない**（Q-2 決定。AC-2）。カードの縦幅と、文字量の段階（§2-3-3）の判定にのみ用いる |
| `blocks[].tasks[]` | ブロックに紐づくタスク |
| `tasks[].shouldPlotOnGrid` | タイムグリッド上への面表示の要否 |
| `violations` | ルール違反アラート（任意。存在時のみ画面上部に一覧表示） |
| `socialJetLagWarning` | 社会的時差ぼけ警告フラグ（`true` 時に警告バナーを表示） |

7 ブロックの ID と表示順序は README の「7 つの時間ブロック」定義に従う。

```
DOWN_TIME → SLEEP_TIME → WALK_TIME → FOCUS_TIME → WORK_TIME → GRADATION_TIME → FREE_TIME
```

**データとしては 7 ブロックを受け取るが、カードとして描画するのは `WORK_TIME` を除く 6 ブロックである。** 縦軸・時刻ラベル・横罫線は、`WORK_TIME` の区間も含めて 1 日全体で連続して描く（§2-3-2）。

### 2-2. ヘッダーと日付ナビゲーション

- 本仕様で「ヘッダー」と呼ぶのは、**表示対象日（`YYYY-MM-DD` 形式）の表示と、「前日」「翌日」の移動導線をまとめた画面上部の領域**を指す。
- ヘッダーの移動導線は Next.js のページ遷移（`<Link>`）を用いるため、**ヘッダーは Next.js 層（`nextjs/app/page.tsx`）に置き、プレゼンテーション層には置かない**（§2-7 の層依存の制約による）。画面高の分割（ヘッダー固定 + グリッドのみスクロール、§2-6）は、Next.js 層とプレゼンテーション層の両方にまたがる。
- **日付の表示は、ヘッダーの 1 か所だけとする（Q-12 決定）。** プレゼンテーション層（`DailyTimeline`）は日付を表示しない。
- **「1 か所」の対象（Q-23 決定）**: この規則が対象とするのは、**画面が自分で組み立てて表示する日付**（ヘッダーの表示対象日）だけである。`TimelineDTO` のデータに由来する日付文字列（タスクのタイトルに含まれる `2026-06-21` や、違反メッセージの中の日付）は**対象外**とし、表示したままにする。Fake のデータ（タスク名）は変更しない。この扱いは AC-7 で検証する。
- プレゼンテーション層は、**1 日の総時間を分数で表示しない**（現行の `DailyTimeline` にある「DOWN TIME 20:30 起点・全 1440 分」のような説明文は出さない）。分数表記を画面のどこにも出さないことは AC-2 で検証する。
- 「前日」「翌日」を押すと、それぞれ 1 日前・1 日後の日付の画面に遷移する。
- 表示対象日は URL クエリ `date=YYYY-MM-DD` で指定する。
- クエリ未指定時のデフォルト日付は `2026-06-21` とする（Fake リポジトリの既定シナリオ日。この日の起点は 20:30。O-1）。
- 日付切り替えは Server Component によるページ遷移（`<Link>` 等）で行う。クライアント側の状態管理や Client Component による日付取得は Phase 1 では行わない。
- 日付の丸バッジ（Google カレンダーの日付サークル）は再現しない。
- ヘッダーはグリッドのスクロールに追従せず、常に画面上部に表示される（§2-6）。

### 2-3. 1 日全体のタイムグリッドとブロックカード

#### 2-3-1. グリッドの構造

- 画面に、1 日全体（`anchorDate` 〜 `anchorDate + totalDurationMinutes`）を縦軸とする **タイムグリッドを 1 つだけ** 設ける。ブロックごとに個別のグリッドは設けない。
- グリッドは横方向に 2 領域で構成する。
  - **左: 時刻ラベル列** — 1 時間ごとの実時刻ラベルを縦軸に沿って並べる。
  - **右: イベント列** — ブロックカードとタスク面を配置する。
- 縦軸の上端は `anchorDate`（当日の DOWN TIME 開始時刻）、下端は `anchorDate + totalDurationMinutes`（＝ 時系列上で最後のブロックである FREE TIME の終端）とする。0:00 始まりにはしない。
- 縦軸のスケールは 1 日を通じて一定とする。1 時間あたりの高さは固定値 **48px** とし、グリッド全体の高さは `totalDurationMinutes / 60 × 48px` とする。したがって 1 日の総時間が変動しても、目盛りの間隔は変わらずグリッド全体の高さだけが変わる。
- **既定シナリオの実値（O-2 / O-3）**: `anchorDate` = 2026-06-21 20:30、`totalDurationMinutes` = **1440 分（24h）**、グリッド全体の高さ = **1152px**、下端 = 翌 20:30。
- 高さの端数は丸めない（`totalDurationMinutes / 60 × 48` をそのまま px として用いる）。分単位の端数があるときは px が小数になる。

> **注（README ルール①との関係）**: README ルール①は 1 日を「当日の DOWN TIME 開始から翌日の DOWN TIME 開始まで」と定義する。標準の日では、下端（`anchorDate + totalDurationMinutes` = 翌 20:30）が起点と同じ時刻になり、この定義と一致する（`day-duration.md` A-3）。第3版に書いていた「下端は翌日の DOWN TIME 開始と一致しない」という注は、標準の日については解消した。
> ただし、**Fake の画面上では一致しない場合がある**。Fake は社会的時差ぼけ警告を再現するために翌日の DOWN TIME 開始を 75 分遅らせており（O-6 / 観測値 21:45）、下端（翌 20:30）と翌日の実際の起点は異なる。翌日の起点を読みに行くのは `day-duration.md` の PBI-D の範囲であり、本仕様の対象外とする。
> **本仕様は、下端を常に `totalDurationMinutes` から決める**（表示側で翌日の起点を参照しない・補正しない）。

#### 2-3-2. 時刻ラベルと横罫線

- 時刻ラベルは **実時刻** を `HH:00` 形式（24 時間表記・Asia/Tokyo）で表示する。DOWN TIME 起点からの経過時間ではない。深夜 0 時は `00:00` と表記する（`24:00` とは表記しない。O-13）。
- **ラベルと罫線を描く位置**: 上端時刻 **以上**・下端時刻 **以下** に含まれるすべての正時（`00` 分）。**正時以外には、上端・下端であってもラベルと罫線を描かない**（Q-21 決定。Q-5 の「実時刻の毎正時」を変えない）。
  - 上端がちょうど正時のとき、上端に 1 本目を描く。下端がちょうど正時のとき、下端にも 1 本描く。
  - 上端・下端が正時でないときは、その時刻にラベル・罫線を描かない（**上端 20:30・下端 翌 20:30 にはラベルが無い**。Q-21 決定）。1 日の始まりと終わりの時刻は、カード内の時刻表記（`20:30〜22:00`）とヘッダーの日付で読む。
  - **既定シナリオ（上端 20:30・下端 翌 20:30）では、`21:00, 22:00, 23:00, 00:00, …, 19:00, 20:00` の 24 本になる**（O-14）。最初のラベル 21:00 は上端の 30 分下（`top` = 2.0833%）に来る。
  - 上端が正時でない日（既定シナリオ、および FOCUS TIME のクッションで起点が分単位で前倒しされた日。例: 20:35）は、最初のラベルが上端より下に来る。上端より前の正時のラベルは描かない（AC-16）。
- 各ラベルの縦位置は、`(ラベル時刻 − anchorDate) / totalDurationMinutes × 100` （％）とする。既存の `calculateTimelineTaskLayout` はタスクを入力とするため、ラベル位置は別の算出関数で求める（既存関数の入出力は変更しない。§5）。
- **罫線とラベルの位置関係**: 横罫線はその正時の位置ちょうどに引く。時刻ラベルは、対応する罫線の **直下**（ラベルの上端＝罫線の位置）に置く。罫線をまたいでラベルを中央寄せにはしない。
- グリッドコンテナの上端・下端に余白は設けない（0% が上端、100% が下端）。ただしスクロール領域の内側で、最下端のラベル 1 行分（16px）の余白をグリッドコンテナの下に置いてよい。この余白は目盛りの一部ではなく、グリッド高さ（§2-3-1）には含めない。
- 時刻ラベルと横罫線は、**`WORK_TIME` の区間も含めて上端から下端まで連続して描く**。カードを描かないブロックがあっても、目盛りは途切れない。
- 上端から下端までの間に日付をまたぐ（例: 23:00 の次が 00:00）が、日付の区切り表示は Phase 1 では行わない。
- タイムゾーン表記（`GMT+09` 等）は表示しない。

#### 2-3-3. ブロックカード

- `TimelineDTO.blocks` のうち、**`blockId` が `WORK_TIME` 以外の 6 ブロック** を、イベント列の上に角丸のカードとして配置する。
- **`WORK_TIME` のブロックカードは描かない。** その区間はカードのない空欄とし、グリッドの背景と横罫線だけが見える。文字列 `WORK TIME` / `WORK_TIME` は、マークアップ全体のどこにも出さない（Q-16 決定。AC-15）。空欄の中には、§2-4 の仕事用タスク面のみを置く。
- 各カードの縦位置（上端）と縦幅は、`anchorDate`・ブロックの `startTime`・`endTime` から算出し、縦軸の目盛り（時刻ラベル・横罫線）と一致させる。**実時間より大きく（または小さく）描いて目盛りとの一致を崩すことはしない。**
- 隣り合うブロックのカードは、時間的に連続しているため隙間なく・重なりなく並ぶ。ただし `WORK_TIME` の区間だけは、その前後のカード（FOCUS TIME の下端と GRADATION TIME の上端）の間が空欄になる。
- **カードの高さに応じた 3 段階の表示（Q-3 / Q-11 決定）**: 1 時間 = 48px 固定のため、px の閾値と分の閾値は 1 対 1 に対応する。

| カードの高さ | ブロックの長さ | 表示する内容 |
| :--- | :--- | :--- |
| **32px 以上** | 40 分以上 | **ブロック名**（`DOWN TIME` のようにアンダースコアを空白に置換した表記）と **`開始〜終了` 時刻**（`20:30〜22:00` 形式）の 2 行 |
| **16px 以上 32px 未満** | 20 分以上 40 分未満 | **ブロック名のみ 1 行**（時刻表記を省略する） |
| **16px 未満** | 20 分未満 | **文字を表示せず、色の帯だけにする**（Q-11 決定）。ブロック名は、支援技術が読めるラベル（`aria-label` 等）として保持する |

- **閾値（16px / 32px）と余白・行の高さの関係（feasibility-v4 G-7 の指摘への対応）**: 閾値は「文字 1 行の高さを 16px、カードの**縦方向の余白を 0**」とした前提で決めている。したがって次のとおりとする。
  - **カードとタスク面の縦方向のパディング（`py-*` / `pt-*` / `pb-*`）とマージンは 0 にする。** 余白は水平方向（`px-*`）だけに付ける。文字は、カードの上端から詰めて置く（垂直中央寄せにしない）。
  - **文字 1 行の高さを 16px に固定する**（`text-xs` + `leading-4` 相当。**未確認: ブラウザでの実際の行の高さは実行して確認していない**。ずれる場合は、行の高さを 16px にする指定を優先する）。2 行の段階（32px 以上）では、2 行の合計が 32px になる。
  - カードとタスク面は、**内容が高さを超えた場合に切り取る**（`overflow-hidden`。1 行の文字が横幅を超える場合も切り取る）。文字がカードの外へはみ出して、隣のカードや目盛りに重ならないこと。
  - この規則は、ブロックカードとタスク面（§2-4）の両方に適用する。
- `durationMinutes`（`90分` 等）は、どの段階でも表示しない。
- 既定シナリオには 40 分未満のブロックが存在しない（最短は GRADATION TIME の 60 分 = 48px。O-3）。**16px 未満**の見た目は、§2-8-1 の確認用シナリオ（`2026-06-28` の FOCUS TIME 10 分 = 8px）で PO が画面で確認する（AC-19）。**16px 以上 32px 未満**（20〜40 分）のブロックは、既定シナリオでも 2 日分の確認用シナリオでも再現しないため、自動テストだけで検証する（Q-19 決定。AC-2）。

#### 2-3-4. 配色と文字色の対応表

- 色は `blockId` ごとに固定で割り当てる。同じ `blockId` は、日付やデータが変わっても常に同じ色になる。色は `TimelineDTO` の値から動的に決めない。
- 実装上は `blockId` → Tailwind クラスの **固定の対応表**（静的な文字列リテラル）で表現する。動的な文字列結合やインライン `style` で色を決めない。対応表に存在しない `blockId` には既定色を割り当てる。

| 対象 | 色の方向性 | 背景（固定クラス） | 文字色（固定クラス） |
| :--- | :--- | :--- | :--- |
| `DOWN_TIME` カード | 薄い青紫 | `bg-indigo-300` | **暗色**（`text-slate-900`）。Q-14 決定 |
| `SLEEP_TIME` カード | 紫 | `bg-purple-700` | 明色（`text-white`） |
| `WALK_TIME` カード | くすんだ茶 | `bg-amber-800` | 明色（`text-white`） |
| `FOCUS_TIME` カード | 赤茶 | `bg-red-800` | 明色（`text-white`） |
| `WORK_TIME` | — | **カードを描かないため色を割り当てない** | — |
| `GRADATION_TIME` カード | 緑 | `bg-emerald-700` | 明色（`text-white`） |
| `FREE_TIME` カード | 青 | `bg-blue-700` | 明色（`text-white`） |
| 仕事用タスク面（`shouldPlotOnGrid: true`） | PO 指定 `#6e72c3` | `bg-[#6e72c3]` | 明色（`text-white`） |
| 対応表にない `blockId`（既定色） | グレー | `bg-slate-600` | 明色（`text-white`） |
| **エラー表示**（`data-timeline-error`。§5 / AC-18） | 暗い赤 | `bg-red-950`（枠線 `border-red-800`） | 明色（`text-red-100`） |

- **エラー表示の配色（`feasibility-v4-delta` F-2 への対応）**: 背景 `bg-red-950`・文字 `text-red-100`・枠線 `border-red-800` とする。コントラストの考え方は、上のカードと同じ規則で揃える（**暗い背景には明色文字を置き、明るい背景の場合だけ暗色文字にする**）。`bg-red-950` は暗色であるため、文字は明色（`text-red-100`）にする。
  - **現行 `page.tsx` の `bg-red-50 text-red-950`（明るい背景 + 暗色文字）は、本仕様では使わない。** ページ全体がダークテーマになるため（§3-1 / Q-6 決定）、明るい背景の面がエラー時だけ現れることになり、他の領域と揃わない。
- **エラー表示の見出し（`feasibility-v4-delta` F-2 への対応。文言は固定しない）**: `data-timeline-error` の要素の中に、**見出し要素（`h1`〜`h6` のいずれか）をちょうど 1 つ**置き、エラーが起きたことが分かる文言をその中に書く。**AC で検証するのは「見出し要素がちょうど 1 つあること」であり、見出しの文言そのものは固定しない**（AC-18）。
  - **この選び方の理由**: ① 見出しの文言はユーザーに見える文章であり、PO が決める範囲である。特定の文言を AC に固定すると、PO が決めていない要求を AC に足すことになる（本改訂は AC の意味を変えない訂正に限る）。② 構造（見出し要素が 1 つ）は測定可能・テスト可能で、文言を変えても AC が壊れない。エラーの内容そのものは `message` の表示で検証する（AC-18）。
  - 実装は、現行 `page.tsx` の文言（「タイムラインを読み込めませんでした」）をそのまま使ってよい。
- **エラー表示の見た目は、PO が画面で確認できない**（URL からエラーを再現する手段が無い。Q-17 決定 / O-12）。したがって、**上のエラー表示のクラス名は、PO が画面を見て承認する対象ではない。** ダークテーマ上で判読できる組み合わせを仕様として固定し、検証を自動テストで行えるようにしたものである（AC-18）。
- **`DOWN_TIME` の文字色だけを暗色にする（Q-14 決定）。** `bg-indigo-300` は明るい背景であり、明色文字ではコントラストが足りないため。背景色は PO 指定のまま変えない。
- **記録のみ（Phase 1 では使用しない色）**:
  - プライベートタスク: `#53839c`。将来グリッド上に表示することになった場合に用いる色として記録する（Phase 1 では表示しない。§1-3 / AC-4）。
  - 「共通」タスク（プライベートとパブリックの両方）: `#606da1`。ドメインに概念がないため Phase 1 では対象外（§1-3）。

### 2-4. WORK TIME 区間のタスク面

- `shouldPlotOnGrid: true` のタスク（仕事用 WORK TIME タスク）のみ、§2-3 のグリッド上に角丸の矩形（面）として表示する。
- **走査の対象は全ブロックの `tasks[]`** とし、`shouldPlotOnGrid` の値だけで表示要否を決める。ドメイン上 `shouldPlotOnGrid` が `true` になるのは「仕事用アカウント かつ `blockId` が `WORK_TIME`」のタスクだけであり、結果として面は `WORK_TIME` 区間の中に描かれる。ただし表示側は、この前提に依存しない。
- **タスク面は、タスクの時刻どおりに描く（Q-15 決定）。**
  - `WORK_TIME` 区間の外に及ぶ時刻のタスクは、区間でクリップせず、そのまま時刻の位置に描く（隣のカードと重なりうる）。データの実態を隠さない。
  - 同時刻に複数の仕事用タスクがあるときは、**全幅で重ねて描く**（後のものが上）。横に等分割して並べることはしない（別 PBI の候補。§1-3）。
- `shouldPlotOnGrid: false` のタスク（プライベートタスク）は、グリッド上には一切表示しない。ブロックに紐づいていても面プロット対象としない（初版 AC-4 を維持）。
- タスク面の縦位置（上端）および縦幅は、`anchorDate`・タスクの `startTime`・`endTime` との関係に基づき、1 日全体に対する割合（%）として算出する（初版から不変。`calculateTimelineTaskLayout` の入出力は変更しない）。
- `endTime` が `null` のタスクは、そのタスクが属するブロックの `endTime` を終端とみなす（初版から不変。**AC-21**）。
- 縦位置・縦幅が算出できないタスク（終了時刻が開始時刻以前、総時間が 0 以下など）は、面を描かない。その場合も、同じブロックの他のタスク面・ブロックカード・目盛りの描画は続ける（**AC-22 ①**）。
- **ただし `totalDurationMinutes` が 0 以下の場合は例外とする（`feasibility-v4-delta` F-5 への対応）**: この場合は 1 日全体に対する割合そのものを算出できないため、**ブロックカードと目盛りも描かなくてよい**。この入力に対して仕様が要求するのは、**例外を投げずに描画を終えること**だけである（**AC-22 ②**）。
- タスク面には、タスクのタイトルと `開始〜終了` 時刻を表示する。**面の高さによる 3 段階の扱いは §2-3-3 と同じ**（32px 以上は 2 行、16px 以上 32px 未満はタイトルのみ 1 行、16px 未満は文字なしの色帯。タイトルは支援技術向けラベルとして残す）。**縦方向のパディング・マージンを 0 にし、内容がはみ出す場合は切り取る**ことも §2-3-3 と同じ（**AC-20**）。
- タスク面の色は `#6e72c3`（`bg-[#6e72c3]`）で固定する。
- `WORK_TIME` のブロックカードを描かないため、「タスク面がブロックカードの記載を覆わないこと」という条件は不要である（第1版案の要求を取り消す）。

### 2-5. 警告表示

（初版から意味は不変。配色をダークテーマに合わせ、Q-13 の決定により高さの上限を定める）

#### ルール違反（violations）

- `TimelineDTO.violations` が存在し、1 件以上の要素を含む場合、画面の最上部（タイムグリッドより前）に警告リストを表示する。
- 各項目には少なくとも `targetTitle` と `message` を表示する。

#### 社会的時差ぼけ（socialJetLagWarning）

- `socialJetLagWarning` が `true` の場合、画面上部に警告バナーを表示する。
- バナーには社会的時差ぼけに関する警告であることがユーザーに伝わる文言を含める。

`violations` 警告リストと `socialJetLagWarning` バナーは両方存在しうる。両方ある場合、画面上部に両方を表示する。

警告表示はグリッドのスクロールに追従せず、常に画面上部に表示される（§2-6）。

- **警告領域の高さの上限（Q-13 決定）**: 警告表示の領域には **最大高さ（画面高の 30%）** を与え、内容がそれを超える場合は **警告領域の内部だけを縦スクロールさせる**。これにより、警告の件数が多くてもグリッドの高さが確保され、ページ全体はスクロールしない（AC-14）。
- **警告領域の目印とクラス（feasibility-v4 G-10 への対応。AC-5 の検証に使う）**: `violations` リストと `socialJetLagWarning` バナーを包む 1 つの要素を「警告領域」とし、`data-warning-area` 属性を付ける。この要素に、最大高さのクラス **`max-h-[30vh]`** と **`overflow-y-auto`** を付ける（いずれも静的なクラス。インライン `style` を使わない）。**`max-h-[30vh]` が Tailwind v4 のビルドで生成されることは、まだ実行して確認していない**（未確認: 静的な arbitrary value なので生成されるはず、という読み取りの推測）。生成されない場合は、同じ意味の静的クラスに置き換えてよい（実装時のレベル1の判断。クラス名を変えたときは AC-5 の検証も合わせる）。`violations` リストには `data-violation-list`、社会的時差ぼけバナーには `data-social-jetlag-banner` を付ける（§3-4）。

既定シナリオでは、`violations` が 1 件（INVALID_MAPPING）、`socialJetLagWarning` が `true` で、どの日付でも両方が再現する（O-6）。**§2-8 の確認用シナリオのうち `2026-06-28`（小さいカードの日）でも同じ状態になる**（`violations` 1 件・`socialJetLagWarning` `true`。O-21）。
**警告が多い状態は、§2-8 の確認用シナリオ `2026-06-30`（警告が多数の日）で再現する**（`violations` は **内部スクロールが起きる件数（初期値 20 件）**。初期値の 20 件は O-25 で観測した値）。この日で、警告領域が画面高の 30% を超えず内部スクロールすること（Q-13 の決定の見た目）を、PO が画面で確認する（AC-5 / AC-14 / AC-19）。
**警告が 1 件も無い状態は、既定シナリオ・確認用シナリオのどちらでも再現しない**ため、その確認は自動テストだけで行う（Q-19 決定。AC-17。Fake で作れること自体は O-9 で確認済み）。

### 2-6. スクロール

- **ページ全体はスクロールしない。** 内部スクロールする領域は、タイムグリッドと、警告表示の領域（最大高さを超えたときのみ。§2-5）の 2 つだけとする。
- グリッド領域は、ヘッダー・日付ナビ・警告表示を除いた残りの表示領域の高さいっぱいを占め、その内部だけが縦スクロールする。
- したがってヘッダー・日付ナビ・警告表示は、グリッドをどこまでスクロールしても画面上部に表示され続ける。
- グリッド内部をスクロールすることで、上端（当日の DOWN TIME 開始）から下端（`anchorDate + totalDurationMinutes`。既定シナリオでは翌 20:30）まで到達できる。
- 初期表示位置はグリッド上端（当日の DOWN TIME 開始）とする。自動スクロールは行わない。
- 時刻ラベル列はイベント列と同じグリッド内にあり、一緒にスクロールする（時刻ラベルの縦方向の固定は行わない）。

### 2-7. 層依存の制約

- プレゼンテーション層（`frameworks-drivers/presentation`）が import してよいのは `@interface`・`@domain`・`@shared` のみとする。`@application` および Next.js 配線（composition 等）への依存は禁止する。
- **プレゼンテーション層の入力は、`@interface` の型のみとする（Q-22 決定による変更）。** 第4版までは「入力は `TimelineDTO` のみ」と書いていたが、Q-22 (b) の決定でエラー表示をプレゼンテーション層に置くことになったため、**`UseCaseError`（`@interface/errors/UseCaseError`）も入力に含める**。`TimelineDTO` と `UseCaseError` はどちらも `@interface` の型であり、上の import の制約は変わらない。`Result` の成功／失敗の判定そのものは Next.js 層が行い、プレゼンテーション層は「タイムラインを描く」「エラーを描く」のどちらかを受け取る（§5）。
- Phase 1 の方針として、Client Component（`"use client"`）および クライアント側の状態管理は導入しない。すべて Server Component で描画する。グリッドと警告領域の内部スクロール（§2-5・§2-6）は CSS のみで実現し、Client Component を導入しない。

### 2-8. 表示確認用シナリオ（Q-10 / Q-19 決定）

PO が既定シナリオでは見られない見た目を画面で確認できるよう、**表示確認専用のシナリオを 2 日分**（Q-19 決定）、Fake / composition に追加する。ドメイン層・アプリケーション層・`TimelineDTO` は変更しない。

| 日 | 開き方 | 確認できること | 対応する AC |
| :--- | :--- | :--- | :--- |
| **小さいカードの日** | `?date=2026-06-28` | 16px 未満のカード（FOCUS TIME 10 分 = 8px）が文字なしの色帯になること（Q-11 の決定の見た目） | AC-2 / AC-19 |
| **警告が多数の日** | `?date=2026-06-30` | 警告が多いとき（`violations` は**内部スクロールが起きる件数**。初期値 20 件）に、警告領域が画面高の 30% を超えず、その内部だけがスクロールし、グリッドの高さが確保されること（Q-13 の決定の見た目） | AC-5 / AC-14 / AC-19 |

#### 2-8-1. 小さいカードの日（`2026-06-28`）

- **開き方**: URL クエリ `?date=2026-06-28`（既定日 `2026-06-21` と、その前日・翌日の導線で到達する日には影響を与えない）。

- **この日の作り方（Fake / composition の構成。feasibility-v4 G-6 への対応）**:
  - 確認用シナリオの `settings`（始業 07:10）は、**その日を表示するリクエストで作る `FakeTimelineRepository` のコンストラクタに渡す**（＝既定シナリオとして与える）。`setScenarioForDate` で `2026-06-28` のキーに設定しない。

## 3. スタイリング方針（What）

### 3-1. テーマ

- 配色はダークテーマとする。背景は暗色、文字は明色。適用範囲は **ページ全体**（`globals.css` の `color-scheme` と `body` 背景、および `nextjs/app/page.tsx` の配色を含む）。
- 警告リスト・社会的時差ぼけバナー・エラー表示も、ダークテーマ上で読める配色にする。
- カード上の文字色は §2-3-4 の対応表に従う（`DOWN_TIME` だけ暗色）。
- **エラー表示（AC-18）はプレゼンテーション層のコンポーネントが描く**（Q-22 (b) 決定。コンポーネントの契約は §5）。その配色（暗色背景 `bg-red-950`・明色文字 `text-red-100`。**§2-3-4 のエラー表示の行**）も、他の配色と同じくプレゼンテーション層の単一の定数で定義し、複数箇所に色を散らさない。

### 3-2. 分担ルール

寸法の基準は初版と同じく「1 日を 100% とする割合（%）」を維持する（グリッドコンテナの高さのみ `px`）。

**単位の定義**:

- グリッドコンテナの `height` のみ **`px`**（`totalDurationMinutes / 60 × 48`。丸めない）。
- 時刻ラベルの `top`、横罫線の `top`、ブロックカードの `top` / `height`、タスク面の `top` / `height` は、すべて **グリッドコンテナの高さに対する `%`**（＝ 1 日を 100% とする割合）。
- 時刻ラベル・横罫線の `top` は `(対象時刻 − anchorDate) / totalDurationMinutes × 100`、ブロックカード・タスク面の `top` / `height` は AC-8 と同じ算出式を用いる。

**% の丸め（feasibility-v4 G-4 への対応。決定: 丸めない）**:

- インライン `style` の `top` / `height` は、**算出した数値をそのまま `%` を付けて出力する**（言語の既定の数値→文字列変換）。小数の丸め・桁の切り捨て・切り上げをしない。60 分の割合は `4.166666666666666%` のようになる（O-23）。
- 根拠: ① §2-3-1 でグリッド高さの px を丸めないと決めており、同じ寸法系の % だけを丸めるのは一貫しない。② 丸めるには `calculateTimelineTaskLayout` の出力を変えるか（AC-8 の「入出力を変更しない」に反する）、描画側に丸めの規則を足す必要があるが、得られる効果は 1152px 基準で 0.001px 未満（O-23）で、見た目に影響しない。③ 丸めると、隣り合うカードの下端と上端の間に、算出式では生じないずれが入りうる。
- **本仕様と AC に書かれた `2.0833%` / `4.1667%` / `0.6944%` などの表記は、読者向けの概数である。** 自動テストの期待値は、丸めた文字列と比較せず、**同じ算出式から作る**（例: `${(30 / 1440) * 100}%`）。

**PO が画面で確認する必要はない**: 上の丸めの規則は、目視では区別できない。検証は自動テストで行う（AC-8 / AC-9）。

| 担当領域 | Tailwind CSS | インライン `style` |
| :--- | :--- | :--- |
| ページ骨格（余白・最大幅・背景・画面高の分割） | 使用する | 使用しない |
| ヘッダー・日付ナビ | 使用する | 使用しない |
| 警告バナー・違反リスト（色・枠線・タイポ・最大高さ・`overflow-y`） | 使用する | 使用しない |
| エラー表示（色・枠線・タイポ。§5 / AC-18） | 使用する | 使用しない |
| グリッドのスクロール領域（高さ・`overflow-y`） | 使用する | 使用しない |
| 時刻ラベル・横罫線（色・タイポ・`absolute` 配置の水平方向） | 使用する | **`top` のみ**使用する |
| タイムグリッドコンテナ（`relative`、罫線） | 使用する | **`height` のみ**使用する（`totalDurationMinutes` に比例するため） |
| ブロックカード（幅・角丸・**背景色**・**文字色**・`absolute` 配置） | 使用する | **`top` と `height` のみ**使用する |
| WORK TIME タスク面（幅・角丸・背景色・文字色・`absolute` 配置） | 使用する | **`top` と `height` のみ**使用する |

インライン `style` が現れるのは上表の 4 箇所だけである。この「許可された属性以外を `style` に書かない」ことは、レンダリング結果の `style` 属性を走査する自動テストで検証する（既存の `DailyTimeline.test.ts` の 1 件は本仕様では必ず失敗するため、書き換える。§5 / O-17）。

- 警告領域の最大高さ（画面高の 30%）は、Tailwind の静的クラスで表す（インライン `style` を使わない）。

### 3-3. 禁止事項

- 動的に算出した値を Tailwind の arbitrary value（例: `top-[${n}%]`）に埋め込まない。§2-3-4 の `bg-[#6e72c3]` のような **静的な文字列リテラル** の arbitrary value は許可する。
- 上表で許可された属性以外のレイアウト属性を、インライン `style` で指定しない。
- ブロックおよびタスク面の色（背景・文字）をインライン `style` や動的な文字列結合で指定しない。§2-3-4 の固定の対応表を用い、対応表に存在しない `blockId` には既定色（`bg-slate-600`）を割り当てる。
- 横罫線を CSS の背景（`repeating-linear-gradient` 等）で描かない。許可されたインライン `style`（`top`）の範囲を超えるため、罫線は 1 本ずつ要素として描く。

### 3-4. 検証のための目印（feasibility-v4 G-4 / G-10 への対応）

AC の自動テストは `renderToStaticMarkup` の出力を走査する。走査の対象を一意に特定できるよう、**次の目印を必ず出力する**。目印は見た目に影響しない（表示される文字列ではない）。目印の名前を変えると AC の検証が壊れるため、**この表がプレゼンテーション層の検証上の契約**である。

| 対象 | 目印 | 備考 |
| :--- | :--- | :--- |
| グリッドコンテナ（高さ `px` を持つ要素） | `data-timeline-grid` | 1 つだけ。`style` に `height` を持つ |
| 時刻ラベル | `data-hour-label="HH:00"` | 値はそのラベルの表示時刻。個数と `top` を AC-9 / AC-16 で検証する |
| 横罫線 | `data-hour-line="HH:00"` | 対応するラベルと同じ時刻を値にする |

| 社会的時差ぼけバナー | `data-social-jetlag-banner` | 同上 |
| エラー表示 | `data-timeline-error` | 1 つだけ。**見出し要素 1 つ**とメッセージを含む要素。**プレゼンテーション層のエラー表示コンポーネント `TimelineError` が出力する**（コンポーネント名・パス・props の契約は §5。Q-22 (b) 決定。AC-18） |

- 目印は `data-*` 属性で表し、**クラス名を検証の目印に使わない**（クラス名は見た目の変更で変わりうるため）。ただし、**ふるまいが仕様で決まっているクラス**（§2-3-4 の配色・文字色、`max-h-[30vh]`、`overflow-y-auto`、`overflow-hidden`）は、そのクラス名自体を AC で検証する。
- 支援技術向けのラベル（16px 未満のカード・タスク面のブロック名／タイトル）は `aria-label` に置く（§2-3-3）。
