## 1. 目的(Why)

プロダクトゴール「前夜の回復(DOWN TIME / SLEEP TIME)を守れている状態を保ち、それがひと目で分かる」を満たすには、**1日の長さそのものが、回復の都合で伸び縮みする**ことをドメインが表現できなければならない。

現状は次の2点で目的を満たしていない。

1. `TimelineCalculator` の `DAY_TARGET_MINUTES = 23 * 60` により、1日の総時間が**常に23時間の固定値**になっている。POによれば、これは暫定の実装であり、意図した仕様ではない。
2. SLEEP TIME は常に標準の7時間で、増減する仕組みがない。社会的時差ぼけからの回復(SLEEP TIME を数日かけて増やす)も、朝の予定に合わせた前倒しも、ドメインに存在しない。

また、カレンダー風UI(スプリント001)は、`TimelineDTO.totalDurationMinutes` を縦軸の下端・グリッド高さの基準として使う。総時間が実態と合っていないと、UIの見た目が仕様どおりでも「1日の区切り」がREADME ルール①と食い違う(`docs/spec/presentation-uc1.md` §2-3-1 の注)。**UIがこのPBIに求めるのは、`totalDurationMinutes` が実際の総時間を返すことだけ**である。

## 2. POの意図と決定(確定。覆さない)

### 2-1. ドメインの意図(スプリント001「ドメインの意図の整理」2026-09-20)

- **P-1**: 1日の総時間は、基本24時間。SLEEP TIME を ±1時間して、23時間や25時間になることがある。
- **P-2**: SLEEP TIME を増減するケースは2つ。
  - ケース①: 前日の遊び予定などで25時就寝になり、社会的時差ぼけが発生した場合に、**数日かけて**1時間 SLEEP TIME を増やして解消する。
  - ケース②: 朝の予定が早いので、1時間早く寝て1時間早く起きる。
- **P-3**: 発動条件は、**睡眠中央時刻のズレが1時間を超えるとき**。
- **P-4**: 総時間の差の吸収は、WORK TIME を短くする / GRADATION TIME をなくす / FREE TIME を短くする、など。
- **P-5**: DOWN TIME 開始も、それに合わせて1時間前後する。
- **P-6**: 現行の `DAY_TARGET_MINUTES = 23 * 60` は暫定の実装で、直す対象。

### 2-2. 論点への決定(2026-09-20。`.work/sprint-002-day-duration/sprint-backlog.md`)

- **D-QD-1 = A(起点のずれ説)**: SLEEP TIME の増減に合わせて **DOWN TIME 開始が ±1時間動く**。起点が動く日だけ、**その前日が23時間、当日が25時間**になる。それ以外の日は24時間。1日の総時間は「当日の DOWN TIME 開始から翌日の DOWN TIME 開始まで」(README ルール①)で定義される。
- **D-QD-2 = B(WORK TIME の標準を9時間にする)**: ~~標準の1日を24時間にする~~ → **D-Q-2 により取り消し**。昼休憩を WORK TIME に含める考え方は D-Q-2 に引き継がれている(標準 9.5時間)。
- **D-Q-1 = A(`DAY_TARGET_MINUTES` を24時間の目標値として残す)**: 1日 = `起点 + 24時間` を目標値(入力)とし、**FREE TIME が残余を受け持つ**構造を維持する。総時間が常に24時間を保つのは、起点が動かない PBI-A の範囲についてである。
- **D-Q-2(標準の1日を、具体的な時刻で確定)**: **起点(DOWN TIME 開始)は 20:30**。内訳は §4-2 の表のとおり(DOWN 1.5h / SLEEP 7.5h / WALK 1.5h / FOCUS 1.5h / WORK 9.5h / GRADATION 1h / FREE 1.5h = 24h)。README の現行の標準との差は **SLEEP 7h→7.5h、WALK 1h→1.5h、FREE 2h→1.5h、WORK 可変→標準9.5時間(始業 08:30)**。
  - 補足(PO確認済み): POの提示画像は WALK 05:30〜06:30(1時間)だったが、POは「WALK 1.5時間(回答のとおり)」を明示した。**回答の時刻が標準**であり、画像は参考にとどめる。
- **D-Q-3(PBI-A の完了判定の範囲)**: PBI-A の完了判定に、**UC-1 画面のPO確認は含めない**。画面の確認は、スプリント001の再開時にまとめて行う。
- **D-QD-3〜QD-8 は未決**: 後続PBIの着手時に決める(§5-3)。
- **先行PBI(PBI-A)**: 標準の1日を24時間にする土台。目的は、UI(スプリント001)のブロッカーの解消。

## 3. 現行実装の事実(変更前に観測した値。推測ではない)

以下は **PBI-A の実装前** の状態である。

### 3-1. 総時間は「入力」であり、FREE TIME が残余になっている

`TimelineCalculator.buildBlocksFromAnchor` は、DOWN → SLEEP → WALK → FOCUS → WORK → GRADATION の順に前から積み上げ、**FREE TIME の終端だけを `anchor + DAY_TARGET_MINUTES` に固定**している。つまり FREE TIME は「残り全部」であり、総時間はブロックの合計(出力)ではなく**目標値(入力)**として与えられている。

### 3-2. 既定値で組み立てた1日の実値(変更前)

`DEFAULT_LIFESTYLE_SETTINGS`(workStart 9:00、workDuration 480分)と anchor 21:00 の場合。

| ブロック | 時刻 | 長さ | README標準 | 一致 |
|---|---|---|---|---|
| DOWN TIME | 21:00–22:30 | 1.5h | 1.5h | ○ |
| SLEEP TIME | 22:30–05:30 | 7h | 7h | ○ |
| WALK TIME | 05:30–06:30 | 1h | 1h | ○ |
| FOCUS TIME | 06:30–09:00 | **2.5h** | 1.5h | **×**(ルール②により WORK 開始まで伸びる) |
| WORK TIME | 09:00–17:00 | 8h | 可変 | —(既定値 480分) |
| GRADATION TIME | 17:00–18:00 | 1h | 1h | ○ |
| FREE TIME | 18:00–20:00(翌日) | 2h | 2h | ○(ただし残余として算出された結果) |
| **合計** | | **23h** | | |

現行の23時間は恣意的な値ではなく、**この既定値の組み合わせで FREE TIME がちょうど標準の2hになる値**である。

### 3-3. SLEEP TIME を1時間増やしても、現行の総時間は変わらない

WORK 開始時刻が `LifestyleSettings` で外部固定されているため、SLEEP TIME が +1h になると **FOCUS TIME が自動的に1h縮む**(ルール②)。SLEEP 8h の場合: WALK 終了 07:30、FOCUS 07:30–09:00(1.5h)。WORK 以降は一切動かない。

つまり、**SLEEP TIME ±1h の吸収は、まず FOCUS TIME が担う**のが現行の構造であり、POが挙げた WORK / GRADATION / FREE の短縮(P-4)が必要になるのは、FOCUS TIME が最小保証の10分に達した後だけである(QD-4)。

### 3-4. `LifestyleSettings.sleepDurationMinutes` は使われていない

`LifestyleSettings` に `sleepDurationMinutes: 420` が定義されているが、`TimelineCalculator` は `getTimeBlockSpec(SLEEP_TIME).defaultDuration`(7h)を読んでおり、この設定値を参照していない。**現状、SLEEP TIME の長さを設定から変える手段はない**(PBI-C の対象)。

### 3-5. DOWN TIME 開始は、日ごとの外部入力である

`TimelineRepository.getDownTimeStart(targetDate)` が日付ごとに独立して返す。**当日の総時間と翌日の DOWN TIME 開始は、現在いっさい連動していない**(PBI-D の対象)。

### 3-6. 社会的時差ぼけの判定は「判定のみ」で、タイムラインを変えない

- `SocialJetLagDiagnostic.diagnose(day, previousDay)`: 各日の SLEEP TIME ブロックの中点を「睡眠中央時刻」とし、**時刻(時分)だけを見た円環差**の絶対値が `>= 60分` なら `hasWarning: true`。
- `SocialJetLagEvaluationService.evaluate(targetDate)`: **当日と翌日**を組み立てて比較する(UC-4)。一方 README ルール⑤は**昨日と当日**の比較と書いている。比較する2日の定義が、文書間で一致していない(QD-5)。
- 判定結果は `SocialJetLagAlertDTO` として返るだけで、SLEEP TIME の長さには影響しない。

### 3-7. 既存テストが置いている前提

| テスト | 前提 |
|---|---|
| `tests/domain/entities/ChronologicalDay.test.ts`「総 duration が 23h〜25h」 | 総時間が 1380〜1500分の**範囲**(23h固定でも通る、緩い検査) |
| `tests/application/usecases/ChangeTimeBoxDurationUseCase.test.ts:223-224` | 同じく 23h〜25h の範囲 |
| `tests/domain/services/TimelineCalculator.test.ts` | 総時間を検査していない。FOCUS ≧ 10分と anchor 前倒しのみ |
| `tests/frameworks-drivers/presentation/*` | DTO を直接組み立てており `23 * 60` をリテラルで使う(期待値も同じリテラルから算出しているため、ドメイン変更では落ちない) |

**総時間を24hに変えても、既存のドメイン・アプリケーションのテストは1件も落ちない**(範囲検査のため)。したがって PBI-A では、総時間を**具体値**で検査するテストが必要になる(A-6)。

### 3-8. README の現行の標準時間の単純合計は、23時間にしかならない

README §① の現行の標準時間を単純に足すと、WORK を9時間としても **1.5 + 7 + 1 + 1.5(FOCUS 標準) + 9 + 1 + 2 = 23時間** にしかならない。現行実装で24時間にならないのも、この標準の不足が理由である。

**D-Q-2 の新しい標準は、単純合計がちょうど24時間になる**: 1.5(DOWN)+ 7.5(SLEEP)+ 1.5(WALK)+ 1.5(FOCUS)+ 9.5(WORK)+ 1.0(GRADATION)+ 1.5(FREE)= **24.0時間**。しかも**既定の設定では FOCUS TIME の実際の長さ(WALK 終了 07:00 〜 始業 08:30 = 1.5時間)が標準値と一致する**ため、「表の合計 = 既定の1日」が成り立つ。第2版で挙げた QD-10(FOCUS の標準1.5時間と実際2.5時間の食い違い)は、この決定により**解消した**(§5-2)。

ただし README の標準時間の表そのもの(SLEEP 7.00時間 / WALK 1.0時間 / FREE 2.0時間 / WORK 可変)は、新しい標準と食い違ったままである。README の修正案は §7 に記す。

## 4. 実現内容(What)

### 4-1. 全体の規則(決定を反映)

- **W-1**: 1日の総時間は、23時間の固定値ではなくなる。**既定の設定では24時間**とする。
- **W-2**: 1日の総時間は、`TimelineDTO.totalDurationMinutes` に、その日の実際の総時間として現れる。
- **W-3**(後続PBI): SLEEP TIME の長さは、**標準7.5時間**(D-Q-2)を基準に、±1時間の範囲で変わりうる。標準より短くする場合も、README の「受動的短縮の禁止」に反しない(能動的理由がある)ものだけを認める。
- **W-4**(後続PBI): 総時間が標準の内訳の合計と異なるとき、どのブロックが差を吸収するかは、決められた優先順位に従う。各ブロックの最小保証時間(Floor)は、吸収によって破られない。
- **W-5**(後続PBI): **1日の区切りは、当日の DOWN TIME 開始から翌日の DOWN TIME 開始まで**とする(D-QD-1)。SLEEP TIME の増減に合わせて DOWN TIME 開始が ±1時間動く日は、その**前日が23時間、当日が25時間**になる。起点が動くとき、README ルール②(FOCUS TIME 10分死守による前倒し)と競合しない。

### 4-2. 標準の1日(24時間)の内訳 — 決定済み(D-Q-2)

**起点(DOWN TIME 開始)20:30、始業 08:30、SLEEP TIME の調整なし**の場合。**PBI-A の完了後、この表が実値になる**。

| # | ブロック | 時刻 | 長さ(分) | 現行の標準からの差 |
|---|---|---|---|---|
| 1 | DOWN TIME | **20:30–22:00** | 90 | 長さは変わらない(1.5h)。起点が 21:00 → **20:30** |
| 2 | SLEEP TIME | **22:00–05:30** | **450** | 420分 → **450分**(7h → **7.5h**) |
| 3 | WALK TIME | **05:30–07:00** | **90** | 60分 → **90分**(1h → **1.5h**) |
| 4 | FOCUS TIME | **07:00–08:30** | **90** | 標準1.5時間は変わらない。**既定の設定では実際の長さも1.5時間**になる(現行は2.5時間) |
| 5 | WORK TIME | **08:30–18:00** | **570** | 480分 → **570分**(標準 **9.5h**。始業 9:00 → **08:30**) |
| 6 | GRADATION TIME | 18:00–19:00 | 60 | 変わらない(1h) |
| 7 | FREE TIME | **19:00–20:30**(翌日) | **90** | 120分 → **90分**(2h → **1.5h**) |

- 下端(`anchor + totalDurationMinutes`)が **起点と同じ時刻(翌20:30)** になる。標準の日では、これが README ルール①の「翌日の DOWN TIME 開始」と一致する。
- **7ブロックの標準時間の単純合計が、ちょうど24時間**になる(3-8)。FOCUS TIME は引き続き「WALK 終了〜始業の隙間」として算出されるが、既定の設定ではその値が標準の1.5時間と一致する。
- FREE TIME は引き続き**残余**として算出される(D-Q-1 = A)。既定の設定では、残余がちょうど標準の1.5時間になる。
- この表は **QD-2(WORK 標準9時間・起点21:00・FREE 2時間)を置き換える**。QD-2 で挙げられた「昼休憩1時間を WORK TIME に含める」という意図は、標準 9.5時間(08:30–18:00)に引き継がれている。

### 4-3. PBI-A(先行)のスコープ

**やること**

- `DAY_TARGET_MINUTES = 23 * 60` の23時間固定を解消し、**1日の目標値を24時間(1440分)にする**(D-Q-1 = A。目標値として残し、FREE TIME が残余)。
- **標準の各ブロックの長さを D-Q-2 に合わせる**: SLEEP 450分、WALK 90分、FREE 90分(標準値のみ。FREE は残余として算出される)。DOWN 90分、FOCUS 標準90分、GRADATION 60分は変えない。
- **既定の生活設定を D-Q-2 に合わせる**: 始業 **08:30**、WORK の標準 **570分**。SLEEP の標準を持つ設定値(`sleepDurationMinutes`)も 450分に揃える(**未使用のまま**。§10)。
- **既定の起点を 20:30 にする**(URL から日付を解釈する既定値と、Fake の既定シナリオ)。これをしないと、§4-2 の標準の内訳が既定シナリオで再現しない。
- `TimelineDTO.totalDurationMinutes` が、その日の7ブロックの長さの合計と一致する値を返すようにする。
- 総時間の回帰を検出できるよう、既存の**範囲検査**を**具体値の検査**に置き換える(3-7)。
- 標準の変更によって**不成立になる既存のテスト値・Fake のデモ値を、成立する値に直す**(§10。例: 社会的時差ぼけを再現するための翌日の遅延幅、プライベートタスクの開始時刻)。

**やらないこと(後続PBIに残す)**

- SLEEP TIME の ±1時間(PBI-C。QD-3 / QD-6)
- DOWN TIME 開始の移動と、23時間 / 25時間の日の発生(PBI-D。QD-1 の適用。QD-6 / QD-8)
- 吸収の優先順位の規則化と、Floor に当たるときの扱い(PBI-B。QD-4 / QD-7 / **QD-11** / **QD-13**)。**PBI-A では、現行の構造(FOCUS TIME = WALK 終了〜WORK 開始の隙間、FREE TIME = 残余)をそのまま維持する**。新しい吸収規則を導入しない。したがって、**始業を 09:30 より後ろにした日(FREE TIME が Floor の30分を割る)と、起点が標準より1.5時間以上遅い日(1日が破綻する)は、PBI-A の対象外**とし、ACにも含めない(§5-2 QD-11 / QD-13)。
- 発動条件(睡眠中央時刻のズレ)の定義(PBI-C / E。QD-5)
- README ルール⑥の新設(§7 R-5。内容が QD-3〜QD-8(未決)と、PBI-B / D に委ねた規則化(QD-11 / QD-13)に依存するため)。※ **§7 R-1〜R-4・R-6 はPOが承認済みで、PBI-A の中で README に反映した**(第4版で訂正。第3版では「README の編集はしない」と書いていた)
- UI仕様 `docs/spec/presentation-uc1.md` の更新(スプリント001の再開時。§8)
- UC-1 画面のPO確認(D-Q-3)

**未決の論点への依存**: PBI-A は、上の「やらないこと」を含まないため、**QD-3〜QD-8(未決)の決定に依存しない**。QD-11 = A / QD-13 = A(いずれも PBI-A の範囲外とする決定)、QD-12 = A(Floor も 1.5時間で固定)は決定済みで、QD-12 はどちらの選択肢でも**観測できる振る舞いが変わらない**(WALK は `isDurationFixed` のため Floor に到達しない)。

### 5-2. 2026-09-20 に決定した論点(**いずれも PBI-A の着手を妨げなかった**)

#### QD-13【**PO決定: A**(前提の事実誤りを受けて再確認し、**2026-09-21 決定済み: A のまま**)。PBI-A の範囲外。PBI-B / D で決める】起点が標準より1.5時間以上遅い日は、1日が破綻する

新しい標準では、WALK TIME の終了は「起点 + 10.5時間」である(標準では 07:00)。始業は 08:30 なので、**起点が標準より1.5時間以上遅い日**は、WALK 終了が始業を追い越し、FOCUS TIME が「翌々日の始業まで」に伸びて、FREE TIME の長さが**負**になる。

- 現行(標準 SLEEP 7h / WALK 1h / 始業 9:00)では、WALK 終了は「起点 + 9.5時間」で、余裕は2.5時間あった。**新しい標準では余裕が1.5時間に縮む**。
- **【第4版で訂正】この日は、静かに壊れるのではなく、未処理の `TypeError` で落ちる。** 1日を組み立てること自体は成功するが、**その日のブロックの長さを読んだ時点で `TypeError: this.range.durationMinutes is not a function` が投げられる**。したがって UC-1 は DTO を返せず、画面は日次タイムラインを表示できない。
  - 事実の根拠(reviewer が起点+2時間で実行して観測し、spec-designer がコードを読んで確認。2026-09-20 / 21): `TimeRange.of` は `tryOf` の戻り値をそのまま `as TimeRange` でキャストするため(`src/domain/value-objects/TimeRange.ts:17-20`)、`start > end` の日では `ScheduledTimeBlock` が保持する値が `TimeRange` ではなく**文字列 `"START_AFTER_END"`** になる。`ChronologicalDay.create` は検証しないので生成は通るが、`ScheduledTimeBlock.duration()`(= `range.durationMinutes()`)を呼んだ瞬間に `TypeError` になる。`TimelineMapper` は各ブロックの `duration()` を必ず読むため、UC-1 の DTO 変換で例外が表面化する。
  - 第3版の「例外は起きない / 画面や集計に不正な値が静かに流れる」は**事実として誤り**だった。静かに流れるのは、例外の前に読まれる `timeRange.start` / `timeRange.end` が `undefined` になる点だけで、**観測できる結末はクラッシュである**。
- 該当するのは、**Fake が社会的時差ぼけ警告を再現するために翌日の起点を2時間遅らせている既定シナリオ**と、既存テストの一部である(§10)。PBI-A では、これらの**値を成立する範囲に直す**(遅延を 1時間15分にする)ことで回避する。

|---|---|---|
| **A** | **PBI-A では値を直して回避し、規則は PBI-B / D で決める** | PBI-A が小さく保たれる。根本の欠陥は残る |
| **B** | PBI-A で、成立しない日の扱い(打ち切り・エラー)を決めて実装する | 堅くなる。ただし QD-4 / QD-7 の先取りになり、PBI-A が膨らむ |

**【第4版】事実の訂正による影響(2026-09-21 決定済み: A のまま)**

- **決定 A の前提が1点、誤っていた**。POは「不正な値が静かに流れる(表示はされる)」という前提で、規則化を後続PBIに回す決定をした。**実際の結末は、UC-1 が未処理の `TypeError` で落ちることであり、影響の大きさが違う**(静かなデータ不正 → 画面が出ない障害)。この事実をPOに共有して決定を再確認した結果、**2026-09-21 に「A のまま」で確定した**(PBI-A は既定シナリオの値を直して回避し、規則化は後続の PBI-B / D)。あわせて、**原因不明の `TypeError` になっている点(`TimeRange.of` の `as TimeRange` キャスト)は、後続 PBI で直す対象として記録する**(どの PBI で扱うかは未決。下の 2. の論点)。

- **PBI-B / D の対策方針への影響(次に決めるときの論点)**: 対策は「静かなデータ不正の検出」ではなく、次の2つになる。

  2. **`TimeRange.of` が `tryOf` の失敗値を `as TimeRange` でキャストして型を破っている欠陥をどうするか**。現状の `TypeError` は、発生箇所(`ScheduledTimeBlock.duration`)と原因(起点が遅すぎる日)がかけ離れており、原因の特定が難しい。この欠陥の扱いは QD-13 の規則化と同じ PBI で決める必要がある。**この点は第3版には無かった論点である**。
